## 2. Application architecture

### Shape

One Next.js app on Vercel. Supabase for Postgres, auth, and row-level security. Claude for classification and question answering, called only from the server. No separate backend in the MVP.

```
Phone / desktop browser (PWA)
        │  HTTPS
        ▼
Next.js on Vercel
  ├─ app/            routes and UI (server components by default)
  ├─ Server Actions  every mutation from the UI
  ├─ app/api/capture POST route for Shortcuts / future voice clients
  └─ lib/
       ├─ db/        Supabase clients (server, browser)
       ├─ domain/    zod schemas + TS types for every object
       ├─ capture/   the capture pipeline (store raw → classify → create item)
       ├─ ai/        provider interface + Anthropic and OpenAI implementations
       └─ retrieval/ queries behind Today, search, and the Assistant
        │
        ▼
Supabase (Postgres + Auth + RLS)          Anthropic API
```

### Route map

| Route | Purpose |
|---|---|
| `/` | Today: overdue, due today, waiting-on, recent captures. Capture bar at top. |
| `/inbox` | Raw captures and low-confidence classifications awaiting review |
| `/projects`, `/projects/[id]` | Project list and everything linked to a project |
| `/assistant` | Ask a question, get an answer grounded in stored items |
| `/items/[id]` | View/edit one task, follow-up, or note |
| `/people`, `/people/[id]` | Everyone the classifier has met, and everything involving one person |
| `/settings` | Password, theme, and the Claude / ChatGPT switch |
| `/guide` | How capture and classification work, with example phrasings |
| `/login` | Magic-link sign-in |
| `/api/capture` | POST, bearer-token protected, same pipeline as the UI |

The capture bar lives in the root layout so it is on every screen. Bottom tab bar on phones: Today, Inbox, Projects, Assistant.

### The capture pipeline

This is the heart of the app and the part that must never lose data.

1. Insert into `inbox_items` with the raw text and status `pending`. Return immediately so the UI feels instant.
2. Call the AI classifier with the raw text, the current date/time in `America/Detroit`, and the user's workspaces, projects, and people as context.
3. Validate the result with zod. Create one `items` row with `kind` task, followup, or note, link people, set dates.
4. Mark the inbox item `processed` and point it at the new item. If confidence is below a threshold, or the workspace/project could not be resolved, mark it `needs_review` instead and still create the item.
5. On any error, mark the inbox item `failed` with the error text. The raw text stays in the inbox. Retry is a button.

Steps 2 to 5 run in the same Server Action after step 1 returns, using `after()` from `next/server` so the request completes first. Vercel functions keep running for `after()` work. If this proves flaky, the fallback is a Supabase cron that picks up `pending` rows, and nothing else changes.

### AI layer

- `AiProvider` interface with two methods: `classify(input, context)` and `answer(question, retrieved)`. The rest of the app depends on the interface, not on Anthropic.
- First implementation: `@anthropic-ai/sdk`, model `claude-opus-5`, structured outputs (`output_config.format`) with the zod classification schema, effort `low` for classification. Adaptive thinking is on by default on this model.
- Cost is not a concern at personal volume. Fifty captures a day at a few hundred tokens each is cents per day.
- Provider and model come from env vars so swapping is a config change.
- The system prompt is static and cached. Volatile context (today's date, workspace list) goes in the user message.

### Retrieval

MVP: Postgres full-text search on a generated `tsvector` column over title, body, and source text, plus structured filters (kind, status, due range, project, person). The Assistant page turns a question into one or more of these queries using tool use, then summarizes the rows. No embeddings in the MVP. `pgvector` is available in Supabase when semantic search is wanted later.

### Auth

Supabase Auth with magic link, single user. `proxy.ts` redirects unauthenticated requests to `/login`. An `ALLOWED_EMAIL` env var rejects sign-ups from anyone else. Every table has RLS on `user_id = auth.uid()`, so even the anon key cannot read another user's rows. The service-role key is not needed for the MVP at all and should not be added until a server-only job needs it.

### PWA

`app/manifest.ts`, icons, and `apple-mobile-web-app-*` meta in the layout. This section originally called for a service worker "for installability"; that turned out to be wrong for this Next version, and Phase 7 dropped it. See section 14. Push notifications are post-MVP and need VAPID keys, a `push_subscriptions` table, and a cron to send them.

### Later phases, designed for but not built

- Voice: the capture bar posts to the same pipeline. Speech-to-text can be the browser's Web Speech API first.
- Remote worker: a `jobs` table plus a signed webhook. The worker polls or is called; the app never runs shell commands.
- CECO: an `integrations` concept where the assistant calls CECO's API as a tool. Nothing in the schema references CECO.

## 3. Data model (Supabase / PostgreSQL)

**DECISION: one `items` table or three.** Proposal: one `items` table with a `kind` column, because "show me everything about Kalamazoo" and the search index are far simpler over one table, and tasks, follow-ups, and notes share most columns. The columns that only apply to one kind are nullable. If this feels wrong, three tables plus a union view is the alternative.

All tables have `user_id uuid not null default auth.uid()` and an RLS policy of `user_id = auth.uid()` for all operations. Timestamps are `timestamptz`.

```sql
-- Areas of life. Seeded by a migration, editable in the UI.
workspaces (
  id uuid pk, user_id, name text, slug text, color text,
  sort_order int, created_at
)

projects (
  id uuid pk, user_id, workspace_id -> workspaces null,
  name text, description text,
  status text check in ('active','archived') default 'active',
  created_at, updated_at
)

organizations (
  id uuid pk, user_id, name text, created_at
)

people (
  id uuid pk, user_id, name text, aliases text[] default '{}',
  organization_id -> organizations null, notes text, created_at
)

-- Everything the user types lands here first. Never deleted.
inbox_items (
  id uuid pk, user_id, raw_text text not null,
  source text check in ('web','api','voice') default 'web',
  status text check in ('pending','processing','processed','needs_review','failed')
         default 'pending',
  ai_result jsonb,          -- full classifier output, kept verbatim
  ai_confidence numeric,    -- 0..1
  ai_model text,
  ai_error text,
  item_id -> items null,    -- set once an item is created
  created_at, processed_at
)

-- Tasks, follow-ups, and notes.
items (
  id uuid pk, user_id,
  kind text check in ('task','followup','note') not null,
  title text not null,
  body text,                -- description / note content / context
  source_text text,         -- original input, copied from inbox for search
  status text check in ('open','waiting','done','archived') default 'open',
  priority text check in ('low','normal','high'),
  due_at timestamptz,       -- task due date or follow-up date
  workspace_id -> workspaces null,
  project_id -> projects null,
  organization_id -> organizations null,
  category text,
  tags text[] default '{}',
  inbox_item_id -> inbox_items null,
  completed_at, created_at, updated_at,
  search tsvector generated always as (
    to_tsvector('english', coalesce(title,'') || ' ' ||
                coalesce(body,'') || ' ' || coalesce(source_text,''))
  ) stored
)

-- Who an item involves. A follow-up "waiting on Matt" is
-- kind='followup', status='waiting', item_people role='waiting_on'.
item_people (
  item_id -> items, person_id -> people,
  role text check in ('waiting_on','mentioned','owner') default 'mentioned',
  primary key (item_id, person_id, role)
)

-- Notes related to other notes/tasks, etc.
item_links (
  from_item_id -> items, to_item_id -> items,
  primary key (from_item_id, to_item_id)
)
```

Indexes: `items(user_id, status, due_at)`, `items(user_id, project_id)`, GIN on `items.search`, GIN on `items.tags`, `inbox_items(user_id, status, created_at desc)`, and a unique index on `lower(people.name)` per user so "Matt" resolves to one row.

How the brief's objects map:

| Brief | Model |
|---|---|
| Inbox item | `inbox_items` row, always kept |
| Task | `items.kind = 'task'` |
| Follow-up | `items.kind = 'followup'`, `status = 'waiting'` while open, `due_at` is the follow-up date, person via `item_people` |
| Note | `items.kind = 'note'`, relations via `item_links` and `item_people` |
| Project, Workspace, Person, Organization | their own tables, nothing hard-coded |
| Reminder | a task with a `due_at`; a push notification later reads the same column |

Migrations live in `supabase/migrations/` and run with the Supabase CLI, so the schema is in git. Generated TypeScript types go to `src/lib/db/types.ts` via `supabase gen types`.

## 6. Implementation phases

Each phase ends with something usable on the phone. Nothing in a later phase is scaffolded early.

**Phase 1. Foundation.** Supabase project, auth with magic link and the single-email guard, `proxy.ts`, migrations for every table above, generated types, seeded workspaces, app shell with bottom tabs, Vercel linked with env vars set. Result: can sign in on the phone and see empty screens.

**Phase 2. Capture and inbox, no AI.** Capture bar writes to `inbox_items`. Inbox page lists them newest first. A manual "make this a task / follow-up / note" control creates the `items` row. `POST /api/capture` with the bearer token. Result: the app is already a usable capture tool, and the data path is proven before AI is involved.

**Phase 3. Classification.** `AiProvider` interface, Anthropic implementation, the pipeline from section 2, confidence threshold, `needs_review` handling, retry. Inbox shows what the AI decided and lets Travis correct it in one tap. Result: typing "follow up with Gary next week about the laptop" produces the right follow-up with the right date.

**Phase 4. Today and item editing.** Today view with the sections from the brief. Complete, snooze, and reschedule from the list. Item detail page for edits. Result: the daily loop works.

**Phase 5. Projects and people.** Project list and detail. People are auto-created by the classifier and viewable. "Waiting on" grouped by person. Result: "what am I waiting on Matt for" is answerable by browsing.

**Phase 6. Search and the Assistant.** Full-text search endpoint. Assistant page: question in, tool-use query planning against the search and structured filters, grounded answer out. Result: all nine MVP items in the brief are met.

**Phase 7. PWA install and polish.** Manifest, icons, service worker, iOS meta tags, install on the phone, keyboard and touch-target pass on every screen.

Rough size: phases 1 and 2 are a day or two each. Phase 3 is the one with the most iteration on prompt quality.

## 10. Phase 3 status

Written on 2026-09-16:

- `src/lib/ai/types.ts` defines the `AiProvider` interface and the zod `classificationSchema` (kind, title, body, priority, due date and time, workspace slug, project name, category, tags, people with roles, confidence, reasoning). Every field is nullable rather than optional because structured outputs need a closed schema.
- `src/lib/ai/anthropic.ts` implements it with `claude-opus-5` via `client.beta.messages.parse` and `betaZodOutputFormat`, effort `low`, a cached static system prompt, and server-side refusal fallbacks (`fallbacks: "default"`). All per-request context (current date in Detroit time, workspaces, projects, known people, the text) goes in the user message so the system prompt cache holds.
- `src/lib/ai/openai.ts` implements the same interface with `gpt-5.5` via `client.responses.parse` and `zodTextFormat`, reasoning effort `low`, and a fixed `prompt_cache_key`. Prompt text lives in `src/lib/ai/prompt.ts` so both providers share it. The schema sent to OpenAI drops string length limits (strict mode rejects them) and the result is re-validated against the full `classificationSchema`.
- `src/lib/ai/index.ts` lists the providers, reports which have keys, and returns the one to use: the user's saved choice when its key is set, else `AI_PROVIDER`, else the first configured. Null when no key is set, in which case captures wait for manual filing.
- `src/lib/ai/preference.ts` reads the saved choice from Supabase auth user metadata (`ai_provider`), with a session client or, for the capture API, the service-role admin lookup. Settings has a Claude / ChatGPT switch that writes it via `auth.updateUser`, so no table was needed.
- `src/lib/capture/classify.ts` runs the pipeline: mark `processing`, classify, resolve workspace and project by name, convert the date with `zonedToIso`, call `promoteInboxItem` with the fields and people, then store the raw result and confidence. Confidence under 0.7 or an unlisted project name leaves the row `needs_review`; a thrown error leaves it `failed` with the message.
- `promoteInboxItem` now updates an existing item in place, so re-filing after the AI picked the wrong kind changes the kind instead of duplicating. People are found by name or alias, created if new, and linked with `waiting_on` or `mentioned`.
- `captureAction` classifies inside `after()` so the capture response returns immediately. The capture bar refreshes the page 3 and 8 seconds later to pull the result in.
- Inbox shows, per row: the AI's proposed kind, title, due date, category and confidence with a "Looks right" button for review rows; a "Retry" button for failures; "Auto-file" for rows captured before the key was set; and the manual kind chips throughout.

To turn it on: add `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` to `.env.local` and Vercel, then pick one in Settings. Models and the fallback provider have defaults.

## 13. Phase 6 status

Written on 2026-09-16:

- `src/lib/retrieval/index.ts` has `searchItems`, a Postgres full-text search over the generated `search` column. Free text becomes an OR'd prefix query ("kalamazoo:* | network:*") after dropping stopwords, because AND misses too much on short notes. It also has `retrieveForQuestion`, which builds the model's context: every open or waiting item (capped at 300) plus full-text hits for the question across all statuses, so notes and finished items are reachable for "what did I say about X".
- `AiProvider` gained `answer(question, ctx)`. Both the Anthropic and OpenAI implementations use structured outputs to return plain-text prose plus the ids of the items the answer relies on. Effort is medium. The answer system prompt is static and cached; the item list and question go in the user message.
- `/assistant` is a GET form so questions are linkable and the back button works. With a key: the answer card, a "Based on" list of the cited items, and "Other matches" from full-text search. Without a key it degrades to plain search. Suggested questions from the brief are one-tap chips.
- No tool-use loop. At personal scale the whole open set fits in one call, which is simpler, deterministic, and cheaper than a query planner. If the item count grows past the cap, the next step is a planning call or embeddings, not a rewrite.

This completes all nine MVP items in the brief. PWA install and polish followed in Phase 7 (section 14).

## 14. Phase 7 status

Written on 2026-09-17. Much of this phase had already landed alongside Phases 4 to 6; what follows is the whole Phase 7 surface, not only the last commit.

- `src/app/manifest.ts` is the `MetadataRoute.Manifest` convention: standalone display, portrait, warm-charcoal background and theme color matching `--canvas`. It builds to a static `/manifest.webmanifest`.
- `src/app/icons/[name]/route.tsx` renders every icon from the logo mark with `ImageResponse`, so there are no binary files to keep in sync with the palette: `192.png` and `512.png` rounded for the manifest, `maskable-512.png` full-bleed with the spark inset to the safe zone, and `apple-180.png` for iOS. Cached immutable for a year. `proxy.ts` skips `/icons/`, so they load before sign-in.
- iOS: `appleWebApp` capable with `statusBarStyle: "default"` and the apple touch icon in the root layout. `viewportFit: "cover"` plus `env(safe-area-inset-*)` in the header and bottom nav keeps content clear of the notch and home indicator. `themeColor` is per color scheme, and `ThemeColorSync` updates it when the Settings toggle forces a theme.
- Touch targets: buttons and the capture send button are 44px or more, bottom-nav tabs are 52px, and `ui.chip` moved from 36px to 44px. Every `ui.chip` call site is interactive; the read-only kind labels use their own smaller shape and were left alone.
- Keyboard: a single `:focus-visible` rule in `globals.css` draws an accent ring on anything focused by keyboard without putting one on every tap. `/` from anywhere focuses the capture box, Enter sends, Shift+Enter adds a line.

**No service worker.** The original plan called for "a minimal service worker for installability". That is no longer true of this Next version — the PWA guide states install prompts work without offline support, and Chrome dropped the service-worker requirement. A hand-rolled cache on an app whose whole point is freshly filed items would buy staleness bugs and nothing else.

Instead, `experimental.useOffline` is on in `next.config.ts`. Next holds navigations, prefetches, and Server Actions while the connection is down and replays them when a `HEAD` poll confirms the origin is reachable, rather than throwing. That covers the case that actually matters: a capture typed in a parking garage is not lost. `src/components/offline-banner.tsx` reads the `useOffline` hook and shows a pill explaining the wait, since a held request otherwise looks like a slow one. It is mounted in the root layout so it covers `/login` too.

The flag is experimental, and `next build` prints it under "Experiments (use with caution)". If it misbehaves, removing the flag and the banner is a two-file revert and the app falls back to failing requests the way it did before. Real offline caching, if it is ever wanted, is Serwist rather than a hand-written worker.

Still manual: installing it to the phone home screen and confirming the icon, splash, and standalone chrome look right on the device.
